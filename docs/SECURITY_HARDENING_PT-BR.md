# Correções de segurança — ArcadeNode

Registro das correções iniciadas em 16/11/2026 sobre a auditoria de `9bd4f9a`. Os 11 grupos de achados receberam correções de código ou configuração. A seção de evidências registra os ensaios locais e em VM Linux. O [guia de implantação](../deploy/README.md#aceite-no-ambiente-de-destino) descreve os testes no ambiente de destino.

## O que mudou

| Achado | Correção implementada | Verificação disponível |
| --- | --- | --- |
| F01 — controle Docker exposto | Compose sem daemon privilegiado, socket do host e portas de API/SQL. Conexão apenas a origens HTTPS cadastradas pelo operador, com mTLS, CA privada, hostname e TLS ≥1.2; redirects/proxy desativados. Tokens de daemon antigos foram retirados das rotas. | API/cliente real contra dois endpoints mTLS simulados; rejeição de certificado ausente, CA/hostname errados e destinos não cadastrados. |
| F02 — console como shell | Removido Docker exec e `/bin/sh -c`; o texto de uma linha é enviado ao stdin do processo do jogo. Entrypoint fixo da imagem; startup arbitrário é recusado. | Captura de bytes do protocolo de attach, sem invocar shell/processos. |
| F03 — limites e quotas | Memória em `checked(long)`, CPU em NanoCPUs, limite de pids/swap, UID 10001, capabilities removidas, raiz somente leitura, tmpfs e logs limitados. Criação normal/cartridge compartilham validação, capacidade e reserva com concorrência otimista e porta única. Disco exige driver de quota verificado; todo o home utiliza um único volume. | Valores exatos para 1/2/4/8 GB, JSON do provisionamento, rejeição de capacidade/portas inválidas e atualização concorrente. Quota efetiva depende do teste físico do driver. |
| F04 — JWT sem revogação | Sessões persistidas e security stamp validados em toda requisição autenticada. Logout revoga a sessão; senha, inativação, papel incompatível e expiração invalidam tokens. Frontend chama logout no servidor, limpa consultas e exige novo login após trocar senha. | Testes HTTP de logout/senha/inativação/papel, JWT adulterado e sessão expirada. |
| F05 — deploy Development/sa/HTTP | .NET em Production, TLS no Nginx, API privada com proxy confiável explícito, arquivos de segredo, manutenção separada de runtime. Conexão SQL cifrada com certificado verificado; runtime rejeita `sa` e grants administrativos efetivos. Containers da aplicação sem root, capabilities e escrita na raiz. | Revisão de configuração e parsing YAML. SQL/TLS/Nginx reais precisam do aceite descrito no guia de implantação. |
| F06 — plataforma/dependências | Backend em .NET 10, pacotes Microsoft/EF 10.0.15 e imagens 10.0; build frontend em Node 24; Axios e transitivos atualizados no lockfile. Removido Swashbuckle sem uso. | Build sem warnings, npm audit e auditoria NuGet, incluindo transitivos. |
| F07 — edição administrativa pelo proprietário | PUT permite somente nome/descrição; recursos, ambiente e startup são recusados, inclusive para administrador nessa rota, pois exigem reprovisionamento consistente. Validação ocorre antes de modificar a entidade. | Usuário proprietário: identificação permitida, campos sensíveis recusados e banco sem alterações indevidas. |
| F08 — IDOR de deployment | Verificação de proprietário ou papel administrativo antes de retornar status. | Usuário A recebe 200; usuário B recebe 403 também na API HTTP completa. |
| F09 — destinos arbitrários | Mesmo cadastro exato e cliente autenticado utilizados no teste e em todas as operações. Não existe daemon padrão implícito; cada operação resolve o node do servidor e confere labels de servidor/node/proprietário. | Endpoints recusados não são contatados; operação no segundo node não chega ao primeiro; labels incompatíveis bloqueiam a operação. |
| F10 — convites | Gerador criptográfico de 16 caracteres, 1–100 usos, expiração padrão de sete dias. Consumo e criação do usuário na mesma transação EF com token de concorrência. Revogação também muda o token. | Duas inscrições concorrentes consomem um único uso; consumidor com estado anterior à revogação é recusado. |
| F11 — disponibilidade | Limites por IP antes da autenticação: 600/min e dez operações concorrentes por IP (64 na aplicação); login/cadastro 20/min; troca de senha 5/min. Listas paginadas (50 padrão/200 máximo), logs até mil linhas e 256 KiB, lote de até cem allocations, corpo de 64 KiB e timeouts. Nginx tem limites adicionais. | Limites HTTP, spoof de X-Forwarded-For recusado, páginas/logs/lotes inválidos e teto de bytes. |

Além dos achados originais, o middleware de auditoria recebeu um DbContext próprio: registrar uma requisição rejeitada não pode salvar alterações pendentes do serviço de negócio. A autenticação aceita apenas `Authorization: Bearer`; não utiliza cookies de autenticação ou credenciais CORS. O middleware CSRF antigo foi removido, eliminando o bloqueio por cookie/token ausente no primeiro login. Isso não elimina o risco de XSS: JWT permanece no sessionStorage, com CSP, React sem HTML bruto e expiração curta. Migrar para outro armazenamento exige uma arquitetura própria, especialmente se passar a usar cookies.

As imagens novas retiram o usuário root, `chmod 777`, senhas padrão e volumes implícitos. Os instaladores e wizards que recriavam a infraestrutura insegura foram aposentados. Os scripts atuais não executam resets de senha, limpeza remota ou implantação automática de nodes.

Foi corrigida também uma corrida entre ligar e suspender servidores. A suspensão é persistida antes de aguardar o Docker, e atualizações de status preservam o estado suspenso por condição atômica. Escritas Docker são serializadas por servidor com `sp_getapplock` transacional no SQL Server. A regressão HTTP cobre a tentativa de suspender durante um start. O ensaio em VM Linux verificou a exclusão mútua do SQL Server entre duas conexões com grants de runtime. [Semântica e permissões do lock na documentação Microsoft](https://learn.microsoft.com/en-us/sql/relational-databases/system-stored-procedures/sp-getapplock-transact-sql?view=sql-server-ver17)

Nas imagens gerenciadas cadastradas pelos aliases documentados, parar e reiniciar enviam `stop` ao console do Minecraft, `quit` ao console do Zomboid ou `SIGINT` ao Reforger. O painel espera até 45 segundos no Minecraft Java e até 90 segundos nos outros três jogos. A operação normal usa a saída confirmada do processo antes de encadear um reinício ou concluir a etapa da agenda. Se o jogo não confirmar a saída esperada, a operação falha e o estado observado continua disponível. **Forçar parada** é uma ação separada e explícita. Na suspensão administrativa o painel aplica a parada do Docker para bloquear a execução. [Cadastro de imagens e operação](../deploy/README.md)

## Migração e compatibilidade

O passo a passo está em [deploy/README.md](../deploy/README.md), com [exemplo de cadastro](../deploy/nodes.example.json), [grants SQL](../deploy/grant-runtime.sql) e [SQL de migração para revisão](security/2026-11-16/security-migration.sql).

- A aplicação não migra o banco ao iniciar. Aplique a migração com identidade de manutenção; produção rejeita runtime administrativo.
- JWTs antigos e convites anteriores são invalidados. Não há redefinição automática de senha de usuário existente.
- Duplicidade de endpoint ou de porta/node aborta a migração antes da alteração do schema. Há verificações para impedir truncamento de endpoint.
- Containers antigos precisam de backup e reprovisionamento com as imagens/políticas novas. Operações são bloqueadas enquanto não atenderem a identificação e o cadastro de confiança.
- Alterações de RAM/CPU/disco/startup pela antiga rota PUT foram desativadas. O redimensionamento transacional com reprovisionamento é uma funcionalidade futura.
- Respostas de listagem agora são limitadas. Consumidores devem enviar `page`/`pageSize` e ler `X-Total-Count`, `X-Page`, `X-Page-Size`. As telas antigas que ainda usam `getAll` mostram a primeira página; controles de paginação completa do frontend precisam ser implementados antes de operar inventários maiores.
- A migração reserva e publica a porta principal e as portas secundárias do manifesto de cada servidor. O plano de importação verifica conflitos no node antes da gravação. [Configuração das portas na migração](MIGRACAO_PTERODACTYL_PT-BR.md)

## Evidências e reprodução

O [harness de regressão](../scripts/security-probes/README.md) inicia a API real em TestServer, com validação/autorização MVC, SQLite temporário e dois endpoints Docker simulados em loopback com mTLS. Usa os serviços reais e o cliente Docker real; não cria containers nem executa comandos. Os certificados e credenciais são sintéticos e os recursos temporários são encerrados ao final.

```powershell
dotnet run --project scripts/security-probes/SecurityProbes.csproj --no-launch-profile
dotnet build scripts/security-probes/SecurityProbes.csproj --no-restore -warnaserror
dotnet ef migrations has-pending-model-changes --project backend/ServerPanel.API/ServerPanel.API.csproj
```

No diretório `frontend`: `npm run build`, `npm run lint` e `npm audit --json`.

**Resultado local:** 28 grupos de regressão passaram; build C# e frontend e lint passaram; nenhuma alteração de modelo pendente da migração; zero advisories no npm e nenhum pacote NuGet vulnerável reportado. [Resultado das regressões](security/2026-11-16/regressions-fixed.json), [npm](security/2026-11-16/npm-audit-fixed.json), [NuGet](security/2026-11-16/nuget-audit-fixed.json). O navegador confirmou dashboard de prévia sem requisições à API e sem erros de console; o bundle de produção continua exigindo autenticação.

O [workflow de regressões](../.github/workflows/security-regressions.yml) adiciona essas verificações a pushes/PRs, valida Compose/shell e prepara build dos containers/teste de configuração do Nginx com seu UID. Foi preparado localmente, sem push nem execução remota nesta sessão. Actions novas estão fixadas por SHA.

Na etapa de observabilidade foram registrados 30 cenários, incluindo os 28 iniciais. A API passou a atribuir códigos de diagnóstico às requisições e os testes verificam que os avisos omitem credenciais e exceções cruas. [Catálogo de diagnósticos](DIAGNOSTICS_PT-BR.md) · [Registro da etapa](security/2026-11-16/diagnostics-regressions.json)

O [relatório original](SECURITY_REVIEW_2026-11-16.md) e os JSON anteriores permanecem como evidência histórica do estado vulnerável; suas linhas/resultados não descrevem o código corrigido.
